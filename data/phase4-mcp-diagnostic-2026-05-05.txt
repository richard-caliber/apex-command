ANALYSIS & RECOMMENDATION (2026-05-05)
══════════════════════════════════════════════════════════════════════

Question put to this diagnostic:
  The connector is registered in Claude.ai and shows 14 tools in connector
  settings, but those tools are NOT surfacing as callable in chat sessions.
  Is the server correctly advertising its tools? Server-side bug or
  client-side issue?

Result: SERVER IS HEALTHY AND SPEC-COMPLIANT END-TO-END.

1. OAuth 2.1 flow ──────────────────────────────────────────────────
   • /.well-known/oauth-protected-resource: returns correct metadata
     (resource, authorization_servers, bearer_methods_supported, scopes)
   • /.well-known/oauth-authorization-server: advertises authorization,
     token, registration endpoints with S256 PKCE
   • DCR (POST /api/mcp/oauth/register): 201 with client_id
   • Authorize POST with valid APEX_API_TOKEN: 302 → claude.ai callback
     with authorization code
   • Token exchange: 200 with access_token (apex-mcp-tok-* bearer)
   • Unauthenticated request: 401 with proper WWW-Authenticate header
     pointing at the protected-resource metadata URL
   ⇒ Conforms to RFC 9728 (resource metadata) + MCP 2025-06-18 auth spec.

2. MCP transport ────────────────────────────────────────────────────
   • POST /api/mcp/mcp returns content-type text/event-stream with
     "event: message\ndata: {...}\n\n" framing
   • initialize: protocolVersion 2025-06-18, capabilities.tools.listChanged
     true, serverInfo present
   ⇒ Streamable HTTP transport, server-advertised version 2025-06-18.
     Current MCP spec is 2025-11-25 but version negotiation is server-led;
     2025-06-18 is the version the mcp-handler@1.1.0 library implements
     and is fully accepted by Claude.ai (it's the same version negotiated
     at deploy verification on 2026-05-04).

3. tools/list response ──────────────────────────────────────────────
   • count: 14 (matches connector UI)
   • Each tool has: name (snake_case, ≤64 chars, valid pattern),
     title, description (<1024 chars), inputSchema with type "object"
     and properties, required array where appropriate
   • All inputSchemas declare "$schema": draft-07 (allowed; clients
     ignore the meta-schema URI)
   • mcp-handler adds an `execution: { taskSupport: "forbidden" }`
     vendor field per tool. This is non-standard but the spec allows
     extension fields and clients MUST ignore unknown fields.
   ⇒ Response perfectly matches the canonical example in
     modelcontextprotocol.io/specification/2025-06-18/server/tools.

4. tool invocation ──────────────────────────────────────────────────
   • apex_list_projects: 200, content[0].type "text", 8035-char text
     payload (formatted "Found 36 project(s)\n\n[...]"). Returned 36
     projects from KV.
   • apex_get_briefing: 200, returns composite Briefing Room view
     (active_projects, your_actions, squad_actions, agent_status,
     blockers).
   ⇒ Response shape { result: { content: [{ type, text }] } } matches
     spec exactly. is_error flag is omitted on success (spec-compliant).

5. Diff vs deploy verify (2026-05-04) ───────────────────────────────
   No regressions. Tool count, schema shapes, OAuth endpoints, and
   response framing are identical to the deploy verification run 24h
   ago. Same 14 tools, same protocol version, same content-type, same

CONCLUSION
──────────
The Apex MCP server is correctly implemented and Claude.ai-compatible.
A working MCP client (this script) successfully discovers all 14 tools
with valid schemas and invokes them through the same OAuth-protected
endpoint Claude.ai uses. The fact that connector settings shows 14 tools
proves Claude.ai's auth-flow + tools/list call also succeeds — otherwise
the count would be 0 or the connector would show an error.

The issue is therefore on the Claude.ai client side. Most likely causes,
in order of probability:

  (a) STATE CACHE DESYNC. The connector record in claude.ai was created
      when the chat-runtime feature flag was off (or the chat session was
      already open before connector registration). Fix: in claude.ai
      Settings → Connectors → Apex, click Disconnect, then Reconnect, and
      open a NEW chat. Tools surface on next session boot, not mid-session.

  (b) PER-CHAT TOOL ENABLE. claude.ai chat UI requires the connector to be
      explicitly toggled on per chat (the "Tools" / paperclip / + menu in
      the composer). Verify the Apex toggle is actually flipped on inside
      a fresh chat — tools registered in Settings ≠ tools enabled in chat.

  (c) ROLLOUT LAG. The 2025-11-20 mcp-client beta header on the API side
      and the equivalent gradual-rollout feature on claude.ai chat might
      not yet be enabled for this specific account/workspace. No user-side
      fix; wait or switch to the API-mode mcp_servers integration as a
      bridge (works today with the access_token captured above).
